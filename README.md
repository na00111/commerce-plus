# 🚀 이커머스 시스템 동시성 제어 기술 백서

> **Commerce-Plus 프로젝트 재고·주문·결제·취소 동시성 아키텍처 보고서 (PR #70)**
> 

## 1. 기능과 정책

본 프로젝트에서는 다중 사용자 요청 환경에서 데이터 일관성과 정밀한 비즈니스 로직 검증을 위해 동시성 제어 제약을 적용하였습니다. 팀 프로젝트 컨벤션 및 도메인 규칙을 기반으로 동시성이 작용하는 핵심 기능과 정책을 정의합니다.

### 1.1 도메인별 필수 규칙 및 동시성 정책

- **공통**
    - `@Auth JwtUser`를 통해 인증 정보를 검증 및 전달받습니다.
    - 상품 재고 차감 및 복구 시 반드시 `Product` 엔티티 내 비즈니스 메서드를 사용합니다.
    - 상품 재고 복구 시에는 `ProductService` 비관적 락 메서드를 사용합니다.
- **장바구니 (Cart)**
    - 로그인 회원의 장바구니를 서버가 조회하며, API 요청 시 `cartId`, `memberId`를 따로 받지 않습니다.
    - 동일 상품 추가 시 새 행을 추가하지 않고 기존 수량을 합산하며, DB 상에 `UNIQUE(cart_id, product_id)` 제약을 설정하여 동시성 생성을 방지합니다.
    - 수량 변경 후 총 수량이 재고를 초과하면 요청을 거절합니다.
- **주문 (Order)**
    - **재고 선차감**: 주문 생성 시점에 재고를 즉시 선차감합니다.
    - **장바구니 유지**: 주문 생성 시점에는 장바구니를 비우지 않으며, 결제 실패 시 바로 재시도할 수 있도록 유지합니다.
    - **주문번호 분리**: 주문번호는 서버가 자동 채번하는 고유값이므로 DB PK와 완전히 분리합니다.
    - 재시도는 새로운 주문 생성으로 처리합니다.
- **결제 (Payment)**
    - 요청 금액과 DB 결제 금액을 각각 검증합니다.
    - 로그인 회원 본인의 주문만 결제할 수 있으며, 타인 주문 결제 시도는 `403 Forbidden`으로 차단합니다.
    - 주문/결제 상태가 모두 `PAYMENT_PENDING`일 때만 결제를 처리합니다.
    - 상태 전이는 `PAYMENT_PENDING → COMPLETED / FAILED`, `COMPLETED → CANCELED`만 허용되며, 그 외 전이는 엔티티 예외로 차단합니다.
    - **결제 성공 시**: 결제 `COMPLETED` + `paid_at` 기록, 주문 `COMPLETED`, 이번 주문에 포함된 장바구니 상품만 비웁니다. (주문 생성 시 이미 선차감되었으므로 재고를 다시 차감하지 않음)
    - **결제 실패 시**: 결제 `FAILED`, 주문 `CANCELED`, 선차감된 재고 전량 복구, 장바구니는 유지합니다.
    - **단일 트랜잭션**: 결제 상태 변경 · 주문 상태 변경 · 장바구니 삭제 또는 재고 복구는 하나의 트랜잭션(`@Transactional`)으로 처리합니다.
    - 모의 결제 단계에서는 외부 네트워크 호출을 배제합니다.
- **취소 (Cancel)**
    - 주문 단위 전액 취소만 지원하며 부분 취소는 금지합니다.
    - **취소 가능 상태 (2가지)**:
        1. 결제 전 취소: 주문 `PAYMENT_PENDING` · 결제 `PAYMENT_PENDING` → 결제 `FAILED`
        2. 결제 후 취소: 주문 `COMPLETED` · 결제 `COMPLETED` → 결제 `CANCELED`
    - 취소 시 주문 상태는 항상 `CANCELED`로 전이되며, 주문 상품 전체 수량만큼 재고를 복구합니다.
    - 이미 `CANCELED`인 주문에 재취소 요청이 오면 중복 재고 복구를 막기 위해 `409 Conflict`를 반환합니다.
    - 주문 상태 변경 · 결제 상태 변경 · 재고 복구는 하나의 트랜잭션으로 처리하며, 결제 완료 후 취소되어도 `paid_at` 이력은 삭제하지 않습니다.

## 2. 정상 실행 흐름

단일 사용자 요청 또는 순차 진입 환경에서의 각 프로세스 흐름입니다.

### 2.1 주문 생성 및 재고 선차감 흐름

1. **[요청 인가]** `@Auth JwtUser`를 통해 인증된 회원 정보 검증.
2. **[상품 정렬 및 비관적 락 조회]** 주문할 상품 ID 목록을 오름차순으로 정렬 후 `ProductRepository.findAllByIdInWithPessimisticLock()` 실행 (`SELECT ... FOR UPDATE`).
3. **[재고 선차감]** `Product.decrementStock(quantity)` 호출 → 재고 부족 시 예외 throw, 정상 시 재고 차감.
4. **[주문 저장]** `PAYMENT_PENDING` 상태의 Order/OrderItem 생성 및 저장 후 트랜잭션 커밋.

### 2.2 결제 승인 및 단일 트랜잭션 흐름

1. **[검증]** 본인 주문 여부(타인 시 403), 금액 일치 여부, 주문/결제 상태가 `PAYMENT_PENDING`인지 확인.
2. **[상태 변경 및 정리]** 결제 및 주문 상태를 `COMPLETED`로 변경, `paid_at` 기록.
3. **[장바구니 삭제]** 이번 주문에 포함된 장바구니 상품만 삭제. (재고 재차감 없음)
4. **[트랜잭션 완료]** 단일 트랜잭션 원자적 커밋.

### 2.3 결제 실패 / 취소 및 재고 복구 흐름

1. **[상태 검증]** 주문이 이미 `CANCELED`인 경우 `409 Conflict` 예외 발생.
2. **[재고 복구]** `ProductService` 비관적 락 메서드를 통해 상품 조회 후 `Product.addStock(quantity)` 호출하여 재고 복구.
3. **[상태 전이]** 결제 `FAILED` 또는 `CANCELED` 변경 후 단일 트랜잭션 완료 (장바구니는 유지).

## 3. 동시 실행 시 문제 (Concurrency Issues)

다중 스레드 환경에서 동시성 제어가 미비할 경우 다음과 같은 비즈니스 오류가 발생합니다.

- **갱신 손실 (Lost Update)**
    - 여러 트랜잭션이 동시 재고 조회 후 차감 시, 나중에 커밋된 트랜잭션이 이전 차감 결과를 덮어써서 재고가 음수가 되거나 실제 판매 수량보다 재고가 적게 깎이는 현상 발생.
- **교착 상태 (Deadlock)**
    - multi-item 주문(예: 상품 A, B) 시 트랜잭션 1이 A→B 순으로, 트랜잭션 2가 B→A 순으로 락을 요청하면 DB 레벨에서 교착 상태 발생.
- **이중 복구 / 이중 차감 (Race Condition)**
    - 동일 취소 요청이 동시에 2건 들어올 때, 상태 검증과 변경 사이의 갭으로 인해 재고 복구가 2번 실행되는 Over-restoration 버그 발생.

## 4. 쓴 코드에서 선택한 해결책 (PR #70 리뷰 반영)

### 4.1 상품 비관적 락 (Pessimistic Write Lock) 적용

재고 차감 및 복구 시 JPA `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 사용하여 DB 수준의 `SELECT ... FOR UPDATE` 쿼리를 실행합니다. 데이터 조회 시점부터 타 트랜잭션의 읽기/쓰기를 배타적으로 차단하여 갱신 손실(Lost Update)을 근본적으로 차단합니다.

### 4.2 상품 ID 정렬 (Sorting Product IDs)을 통한 데드락 예방

다중 상품 주문 시 발생할 수 있는 교착 상태(Deadlock)를 방지하기 위해, 락을 획득하기 전 항상 **상품 ID(PK)를 오름차순으로 정렬**한 뒤 정렬된 순서대로 락을 획득합니다.

Java

```
// 데드락 방지용 ID 정렬 및 비관적 락 조회
List<Long> productIds = request.getItems().stream()
    .map(OrderItemRequest::getProductId)
    .sorted() // PK 기준 오름차순 정렬하여 락 획득 순서 고정
    .collect(Collectors.toList());

List<Product> products = productRepository.findAllByIdInWithPessimisticLock(productIds);
```

### 4.3 원자적 엔티티 상태 검증 및 단일 트랜잭션 결합

취소/결제 처리 시 엔티티 내부 검증 메서드(`validateCancelable()`)를 두고, 상태 변경 · 재고 복구 · 장바구니 삭제를 하나의 `@Transactional`로 묶어 DB 일관성을 보장합니다.

### 4.4 UNIQUE 제약조건 활용

장바구니 동일 상품 중복 생성을 막기 위해 DB 상에 `UNIQUE(cart_id, product_id)` 제약을 선언하여 동시 요청 시 DB 레벨에서 즉시 차단합니다.

| --- | --- | --- | --- | --- |
| 비관적 락

| 낙관적 락

| 분산 락

(Redis Redisson) | Redis 등 외부 인메모리 저장소를 활용하여 애플리케이션 외부에서 락 제어. | - 분산 서버 환경에서 DB 부담 없이 동시성 제어

- 타임아웃 세밀 조정 가능 | - Redis 인프라 구축 및 관리 비용

- 네트워크 I/O 오버헤드 | **❌ 미선택**

현재 단일 DB 커넥션 환경 및 아키텍처 단순성 유지를 위해 DB 비관적 락으로 충분히 해결 가능. |

## 6. 트랜잭션과 락 범위 (Transaction & Lock Scope)

### 6.1 트랜잭션 및 락 바운더리 최적화

- **락 획득 시점**: 비즈니스 로직 진입 후, 실제 재고 차감 및 검증이 필요한 DB 조회 시점에 `FOR UPDATE` 락을 최소한으로 획득합니다.
- **외부 I/O 결합 금지**: 모의 결제 및 외부 PG 연동, 이메일/알림톡 발송 등 시간이 오래 걸리는 I/O 작업은 락을 보유한 트랜잭션 내부에서 절대 수행하지 않습니다. (팀 컨벤션: 모의 결제 단계에서는 외부 네트워크 호출 배제)
- **트랜잭션 최소화**: 주문 생성(재고 선차감) 트랜잭션과 결제 승인/상태 변경 트랜잭션을 분리하여 각 트랜잭션의 점유 시간을 최소화함으로써 DB 커넥션 풀(HikariCP) 고갈을 방지합니다.

### 6.2 데이터베이스 커넥션과 락 해제 메커니즘

## 비관적 락은 `@Transactional`이 종료되는 커밋(Commit) 또는 롤백(Rollback) 시점에 자동으로 해제됩니다. 따라서 트랜잭션 내부에 불필요한 로직을 배제하여 락 보유 시간을 최소화하는 것이 핵심입니다.
